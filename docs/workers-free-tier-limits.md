# Cloudflare Workers 免费版额度说明

Workers 免费版对单个请求和每天的使用量都有硬限制，超出后要么请求被杀（CPU 超限 → Error 1102），要么直接抛异常（如子请求超限的 `Too many subrequests`）。本项目各功能在设计时都围绕这些额度做了预算和降级，本文汇总各限制的来源和项目内的应对方式。

> 付费版（$5/月起）额度扩大 100 倍以上，基本无需关心下述细节。

## 平台限制总览

| 资源 | 免费版 | 付费版（$5/月起） | 说明 |
| --- | --- | --- | --- |
| CPU 时间/请求 | 10ms | 默认 30s，可调至 5min（等待网络 I/O 不计入） | 超限请求被杀，返回 Error 1102 |
| 子请求数/请求 | **50** | 10,000 | 每次 `fetch()`（含 R2 S3 API 调用、KV 操作）算 1 次 |
| 内存/isolate | 128MB | 128MB | 大文件不能整体读入内存，必须流式处理 |
| KV 写入/天 | 1,000 | 100 万 | 每天约写 1000 个 key |
| KV list()/天 | 1,000 | 10 万 | 项目内任务列表轮询已避开 `list()`，见 [离线下载文档](webdav-and-offline-download.md) |
| KV get()/天 | 10 万 | 1,000 万 | 配额是 list() 的 100 倍，轮询读走 get() |

## 各功能的子请求预算（免费版 50 次/请求）

批量操作类接口最容易撞子请求上限，各接口的设计预算如下：

### 批量删除文件（`/api/delete-batch`）

- 单次 `DeleteObjects` 调用 = **1 个子请求**，最多携带 500 个 key。
- 前端按 500 个文件一批分批调用，每批子请求恒为 1，安全。

### 批量删除文件夹（`/api/delete-tree`）

- 每个文件夹前缀至少 **2 个子请求**：1 次 ListObjects（每页 1000 个对象）+ 1 次 DeleteObjects（每批 500 个对象）。
- 即每个前缀约 `1 + ⌈对象数/1000⌉ + ⌈对象数/500⌉` 个子请求。
- **前端按 10 个前缀一批分批调用**（每批约 20 个子请求起步，留有余量），避免一次请求把 50 个子请求额度烧光导致 500。
- 边界：单个文件夹对象超过约 **1.6 万个**时，即使单个前缀也会超限。此时 Worker 会检测到 subrequest 错误并立即中止，返回 **207**（Multi-Status）+ 已删数量 + 错误明细，不会裸 500 也不会静默丢失。
- Worker 端对所有 List/Delete 调用都有 try/catch，单个失败会累积到 `errors` 数组返回，不影响其他前缀继续执行。

### 大文件改名/移动（multipart 分片拷贝）

- 分片数上限 `COPY_MAX_PARTS = 30`（init + ≤30 分片 + complete ≈ 32 个子请求），就是为了防子请求超限。
- 64MB 以上文件走 multipart 并行拷贝（并发 6），以下走整体 CopyObject。

### 离线下载

- 预算 ≈ 44 个子请求：源站 fetch + R2 PUT + 进度写（10 次 × 每次 4 个子请求），刚好够单文件直传。详见 [离线下载文档](webdav-and-offline-download.md#workers-平台限制来源为什么免费版只能下小文件)。

## 失败兜底约定

- Worker 注册了全局 `app.onError`，任何未捕获异常返回 JSON `{ error: "..." }`（500），前端能显示具体原因而不是空白报错。
- 部分失败的批量操作返回 **207 Multi-Status**，响应体带 `deleted`（成功数）和 `errors`（失败明细）；前端会提示「删除完成，N 项失败」。

## 实践建议（免费版）

- 批量删除文件夹时单次选择不要超过 **30 个左右**（前端已按 10 个/批自动分批，一般无需关心）。
- 单文件夹对象数控制在 1 万以内；超大目录建议先删内容再删空壳，或改用 Node/Docker 自托管版。
- 需要大量批量操作、大文件、WebDAV → 用 [Node/Docker 自托管版](../README.md#docker-部署)，无这些平台限制。
